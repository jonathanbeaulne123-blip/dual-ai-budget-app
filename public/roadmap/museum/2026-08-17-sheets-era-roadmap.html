Two of the original four defects are fixed. Three more turned up in a deep, formula-level review of the actual live workbook — the first one below is arguably the single most important finding of this whole project so far, since it means a flagship feature has been silently not doing what its own menu label says. The top two are now fully scoped, value-verified against the live workbook, and confirmed by Jonathan — queued for delivery, not yet applied (see the batching note below).
Critical · confirmed, queued
Budget's "Budgeted" column is disconnected from Budget Plan for 15 of 18 expense categories Budget!C14:C27 and C31 (Rent, Gas, Electric, Groceries, and 10 more) are plain static numbers — not formulas — left over from before Budget Plan existed. Monthly Budget Sit-Down and the roll-forward tooling correctly write real numbers into Budget Plan every month, but the Budget page never reads any of it back for these rows, so it keeps showing stale figures typed in long ago (Electric's "$30,000/mo budget" is the tell). Re-verified directly against the live workbook's actual formula source on 2026-08-17: fix is the same live SUMIFS('Budget Plan'!...) pattern already used on C28. Confirmed impact for August 2026 — Rent $1,000→$3,300, Electric $30,000→$116, Debt $5→$250, Subscriptions $2→$460, and 11 more; Total Expenses Budgeted goes from a meaningless $34,264 to a real $6,546.50. Jonathan confirmed the fix; execution is batched with the item below into one end-of-session document edit (see note below).
Critical · confirmed, queued
Hardcoded SUMIFS range bounds will silently start dropping data 16 of 21 Budget category rows' Actual/Budgeted formulas (plus all 240 real formulas on Income History) bound their Transactions/Budget Plan lookups to a literal row count ($5:$33, $5:$78) frozen at whatever the row count happened to be when the original "fix Excel Table fragility" pass ran — not a real generous buffer. Currently dormant (Transactions has only 5 real rows today), but the next transaction that pushes past row 33 would quietly freeze every $33-bound Actual total — no error, just stale numbers that look fine. Re-verified directly against the live workbook's actual formula source on 2026-08-17 (exact cells: Budget!C6:C8, D6:D8, D14:D25, D31, and Income History!B6:C125). Jonathan confirmed the fix; execution is batched with the item above into one end-of-session document edit (see note below).

Phase 1.6 · added 2026-08-17 (night), from a deep formula audit

Formula & Performance Hardening

Not started

A direct uploaded copy of the live workbook let this pass read actual formula source (not just rendered values) for the first time. The headline finding: the spreadsheet's native formulas — not Code.gs — have their own version of the exact "fragility" bug the original audit fixed, just better hidden. These are all proposals; nothing here is built without a separate go-ahead.

0 / 10
  • ○Wire Budget's expense "Budgeted" cells to Budget Plan via live SUMIFS, the same way Income rows already work
  • ○Bump every hardcoded SUMIFS/AVERAGEIF bound (Budget, Income History, Budget Plan refs) to the same generous convention Code.gs already uses
  • ○Add a formula-bound sanity check to Show Version & Diagnostics
  • ○Duplicate-category-name guard in Add Category
  • ○Data-validation dropdowns on Budget's manually-typed columns, matching Transactions' existing discipline
  • ○Bring Income History under header-based lookup + diagnostics coverage
  • ○Right-size Income History (121 pre-built months of live formulas is 10 years of mostly-guaranteed-zero recalculation)
  • ○Range protection on formula/ID-helper columns, so an accidental manual overwrite fails loudly instead of silently
  • ○1-click Fixed/Fluctuating recategorize — add a Categories!Income_Stability_Default dropdown (instant, no dialog) and/or a rerunnable "Recategorize" quick-action that only lists categories flagged for review, instead of re-running the full one-time Classify tool
  • ○Rename Income's Category_ID from bare "INCOME" to "CAT-INCOME" for full naming consistency with every other top-level category — a real data migration, not a code change: needs a full audit of every Parent_Category_ID/formula/filter that references "INCOME" first, then one atomic, confirmed update. Deliberately deferred (see v0.0.19 note below) rather than bundled into a bug fix.

Update 2026-08-17 (later still): Jonathan stress-tested Add Shift live and caught a real data-integrity bug — the two auto-created "Wages"/"Tips" subcategories had Parent_Category_ID = "CAT-INCOME", a value that doesn't match any real Category_ID in the live Categories sheet. Direct inspection of that sheet showed the actual top-level Income category's ID is the bare string "INCOME" (an intentional, documented exception to the "CAT-" prefix used by every top-level Expense category) — meaning v0.0.17's earlier "fix" (which changed this from "INCOME" to "CAT-INCOME" based on legacy Transaction rows' derived reference fields) was itself wrong, sourced from an orphaned reference in the original migration rather than the authoritative Categories table. Reverted in v0.0.19: addCategory(), ensureIncomeSubcategory_(), and postShiftTransaction_() all now correctly use "INCOME". The two already-created live rows need a one-time manual correction (Categories!B41 and B42, "CAT-INCOME" → "INCOME"). A separate idea — actually renaming Income's real Category_ID to "CAT-INCOME" for full consistency — was captured instead of rushed, since that's a live-data migration requiring its own scoped audit; see the new Phase 1.6 item above.
