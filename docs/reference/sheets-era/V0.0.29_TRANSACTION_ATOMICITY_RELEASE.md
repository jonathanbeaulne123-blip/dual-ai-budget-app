## Goal

Every accepted Add Transaction submission must create exactly one complete `Raw Transactions` / `Transactions` row pair and exactly one corresponding manual-batch count increment. Two overlapping Add Transaction executions must serialize, allocate unique IDs, and never stale-overwrite one another's plan.

## Commit boundary

`addTransaction()` now has two validation passes:

1. A fast read-only preflight rejects ordinary malformed, stale, or tampered requests without waiting for the write lock.
2. After a document lock is acquired, the current categories, members, account, timezone, and Toronto date representation are read and validated again. Only this under-lock result is authoritative.

The lock is then held across current-state reads, deterministic planning, batch mutation, both row writes, flush/verification, and any required rollback. A 10-second timeout makes zero writes and asks the user to retry.

## Pure planning and guarded execution

`planManualTransactionCommit_()` accepts normalized plain input plus plain current state. It returns:

- unique next `TXN-MANUAL-*` and `RAW-MANUAL-*` IDs;
- intended target rows;
- whether `BATCH-MANUAL-ENTRY` already exists;
- its verified prior and intended next `Record_Count`; and
- complete direct record objects for the batch, raw row, and transaction row.

The Sheet adapter prepares header-mapped row arrays and all three same-row formulas before the first mutation. `Effective_Category_ID`, `Effective_Subcategory_ID`, and `Duplicate_Key` are included in the single Transactions row append rather than written as three later cells.

`executeManualTransactionCommit_()` journals each stage before calling the injected adapter:

1. update or create the manual batch;
2. append the raw row;
3. append the complete transaction row; and
4. verify the batch count, exact linked pair, and helper formulas.

If a stage or verification fails, all attempted mutations are reversed in order: transaction row, raw row, then batch restoration/removal. Rollback locates only the stable IDs allocated by that attempt and refuses ambiguous or drifted targets. It then flushes and re-reads all three targets to prove the original state was restored. Complete recovery returns a clear not-saved error. Incomplete or unverified recovery returns a `CRITICAL` error telling the user not to retry until development data is inspected.

## Post-commit boundary

The duplicate-review engine also uses a document lock, so it runs only after the atomic transaction lock is released. Change logging and summary refresh are also post-commit concerns. If the durable pair is saved but duplicate refresh fails, Add Transaction returns success with a manual-refresh warning instead of a normal failure that might prompt the same financial transaction to be submitted again.

`Potential_Duplicate_Flag` remains derived review state and `Is_Duplicate` remains the separate financial control. This candidate does not change duplicate policy or financial calculations.

## Automated verification

`scripts/test-transaction-atomicity.mjs` covers:

- deterministic IDs, target rows, record construction, and batch increments;
- planner immutability and invalid/duplicate batch configuration;
- sequentially serialized submissions receiving unique transaction/raw IDs and complete pairs;
- success through the real Sheet-adapter shape with all three helper formulas in one row append;
- failures before and after each of the three mutation stages;
- verification failure after all writes;
- exact state restoration plus a post-rollback re-read, including an adapter write that completes and then throws;
- row-extent drift between planning and append, proving the attempt restores its batch mutation while preserving the unrelated row that caused the abort;
- continued reverse-order recovery when one rollback action itself fails;
- a loud critical error when recovery is incomplete;
- lock timeout, authoritative under-lock revalidation, release on success/failure, and post-lock derived refresh ordering; and
- saved-with-warning behavior for a post-commit duplicate-refresh failure.

The complete test command also keeps all v0.0.24-v0.0.28 migration, duplicate-review, and validation guarantees green.

## Deliberate scope boundary

- Add Shift has a different multi-record workflow and remains outside Issue #6. It does not yet share this rollback plan.
- A document lock serializes Apps Script executions that acquire it; it does not prevent direct human edits in the Google Sheets UI. Stable-ID verification and conservative rollback reduce that risk without claiming a database transaction that Sheets cannot provide.
- Repeated full-table stable-ID reads are accepted as a non-blocking current-scale limitation and tracked separately in [Issue #14](https://github.com/jonathanbeaulne123-blip/dual-ai-budget-app/issues/14). Optimizing them must preserve fresh commit/recovery verification.
- Currency metadata remains unchanged here. Issue #10 owns the guarded USD-label-to-CAD correction.
- Production deployment and unrelated financial calculations are excluded.
