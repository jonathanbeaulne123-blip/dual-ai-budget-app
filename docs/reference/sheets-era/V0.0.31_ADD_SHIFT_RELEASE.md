# v0.0.31 Add Shift End-to-End Candidate

## Task packet

- **Task ID:** GitHub Issue #2 — Tip Tracking and Add Shift end-to-end
- **Goal:** Make one tipped shift understandable before submission and reliably produce one Wages plus one Tips ledger record from configurable rules.
- **Why it matters:** Add Shift writes financial source data and four linked ledger rows. Preview drift, weak validation, concurrent IDs, or a partial write can misstate income and be difficult to reconcile later.
- **Risk level:** High — financial calculation and a multi-sheet write workflow.
- **Default lead:** Codex implementation and integration; Gemini independent review; Jonathan explicitly waived Claude review for this issue and controls development deployment and production approval.

## Accepted behavior

- Sales, cash tips, credit-card tips, and hours accept nonnegative values with no more than two decimal places. Hours are required, greater than zero, and no more than 24.
- The current named-range settings remain configurable without code changes: floor percentage, bar percentage, bar rounding increment, credit-card percentage, and hourly wage.
- Floor, bar, credit-card tip-out, net tips, and wages are normalized to cents. A negative net-tip result remains allowed for compatibility but appears as a warning before and after posting.
- `BATCH-SHIFT-ENTRY.Record_Count` counts submitted source shifts. Each source shift derives two Raw Transactions and two Transactions rows; the batch note states this meaning.
- A same-member, same-date prior shift produces a confirmable warning. A different member on that date does not trigger the warning, and a legitimate double shift remains possible.
- Historical Tip Tracker rows are preserved exactly and keep blank Shift IDs. New rows receive stable `SHIFT-000001`-style IDs and a JSON snapshot of the calculation settings used.

## Runtime design

### One calculation for preview and posting

The dialog calls `getShiftPreview()`. The posting path calls the same pure `calcShiftAmounts_()` function after authoritative server validation. No tip-out or wage formula remains in browser JavaScript.

The preview returns a settings fingerprint. `addShift()` compares it before locking and again after re-reading settings under the document lock. If rules changed, the server returns a fresh preview and writes nothing until the user reviews and submits again.

### Validation boundary

`validateAndNormalizeShiftInput_()` accepts plain data and verifies:

- a real `YYYY-MM-DD` date under `America/Toronto`;
- an active household member;
- exactly one active account using authoritative CAD metadata;
- exactly one active Wages and one active Tips income subcategory;
- whole-cent sales and tip fields; and
- positive hours no greater than 24.

The browser is a usability layer, not a trust boundary. The server completes a read-only preflight before taking a lock, then repeats all authoritative reference reads, validation, and date parsing under the lock before reading commit state.

### Serialized first-use setup

Opening Add Shift may install the two previously blank Tip Tracker audit headers or create missing Wages/Tips Income subcategories. `ensureShiftInfrastructure_()` holds one document lock across that complete check/create sequence, so simultaneous first-time dialog opens cannot provision duplicate categories. A lock timeout begins no setup work and asks the user to reopen the dialog.

### Stable source event and atomic write

`planShiftCommit_()` creates one immutable plan from the locked state:

1. one Shift ID;
2. one shift-batch prior/new count;
3. one Tip Tracker source row;
4. two Raw Transactions rows, Wages and Tips; and
5. two Transactions rows, Wages and Tips, including all three helper formulas.

All four write stages run under one document lock. The adapter verifies exact dates, amounts, member, account, currency, categories, stable links, batch count, and formulas. A failure before or after any write stage triggers reverse-order rollback and a final proof that the previous state was restored. Ambiguous or incomplete recovery fails loudly and instructs the user not to retry.

Duplicate flags, Budget/Dashboard/Income History, and Change Log run only after the durable commit and lock release. Their failure is reported as saved-with-warning rather than as a normal submission failure.

## Sheet layout transition

The first v0.0.31 opening of **Add Shift** validates the existing 12 Tip Tracker headers, then adds two headers only in the previously blank columns:

- `Tip Tracker!M9`: `Shift ID`
- `Tip Tracker!N9`: `Calculation Settings`

No historical shift row is backfilled or rewritten. If either destination column is already used for another purpose, setup aborts instead of overwriting it.

## Diagnostics and health

- Version & Diagnostics reports the configured rules plus counts of stable-ID and preserved historical rows.
- Data Dictionary documents Shift ID and its two source-link fields.
- Data Health Check validates every new stable shift across Tip Tracker, Raw Transactions, and Transactions: one source, one Wages and one Tips row per ledger layer, amount agreement, account, member, currency, type, subcategory, raw-to-transaction linkage, and settings metadata.
- Historical rows with blank Shift IDs remain outside the new linkage check.
