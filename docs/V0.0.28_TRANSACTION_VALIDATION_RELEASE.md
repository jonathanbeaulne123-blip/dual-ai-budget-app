## Goal

A stale, altered, or malformed Add Transaction request must fail before any Import Batches, Raw Transactions, Transactions, Change Log, duplicate-review, or summary write can occur.

## Authoritative contract

`validateAndNormalizeTransactionInput_(form, referenceData)` accepts and returns plain JavaScript data without calling Spreadsheet services. It enforces:

- exact supported types: `Income` or `Expense`;
- a real `YYYY-MM-DD` Gregorian date interpreted under the accepted `America/Toronto` runtime standard;
- a finite positive amount that normalizes to an exact integer number of cents;
- an active leaf category selected from authoritative server-read data;
- exact category/type agreement;
- an active nonblank household member, while blank remains Joint/Shared;
- a nonblank active account selected by the existing single-account adapter; and
- trimmed plain-text notes.

The normalized result contains the stable IDs and authoritative category metadata used by the write adapter. Browser-provided display names or category metadata are never trusted.

## Zero-write boundary

`addTransaction()` reads the current active categories, members, account, and spreadsheet timezone, passes them with the request into the pure validator, and parses/round-trips the validated Toronto date. Only after all of those steps succeed may it call `getOrCreateManualBatch_()`, the first write-capable helper.

This closes Issue #7's validation scope. It does not make the later valid-request writes atomic: Issue #6 will revalidate under one document lock, allocate IDs, update the batch, commit both ledger rows/formulas, and recover from partial failure. Issue #10 separately replaces known incorrect USD metadata with account-derived CAD labels without converting amounts.

## Automated verification

`scripts/test-transaction-validation.mjs` covers:

- valid Expense and Income normalization;
- leap-day and Joint/Shared boundaries;
- ordinary floating-point noise normalized to exact cents;
- unsupported and case-altered transaction types;
- malformed and impossible dates;
- blank, zero, negative, nonnumeric, non-scalar, unsafe, and fractional-cent amounts;
- stale/inactive categories and household members;
- tampered category/type combinations;
- wrong timezone and missing account configuration;
- reference-data immutability and the absence of Spreadsheet services in the pure validator;
- zero write-capable calls for every rejected request; and
- zero write-capable calls if Toronto date parsing fails after pure validation.

Gemini's independent review returned APPROVE. The follow-up commit also adds direct malformed root-form/reference-data cases and proves a valid request completes the Toronto parse/format round-trip before reaching the first write-capable helper.
