## How to use this gate

This is the single go/no-go roll-up for meaningful October household data. A control is green only when its `status` is `production-ready` and the automated and manual evidence prove the exact Production environment. Development evidence can move a row to `development-verified`; it can never make Production ready.

“Implemented” means code or a repository contract exists. “Verified” means the named proof was actually run and its receipt is retained. An applied migration number is historical evidence, not permission to reapply it. Every manual action has a named owner, rollback, and evidence destination before it starts.

## Status vocabulary

- `blocked` — a required control, owner action, or exact-environment proof is missing.
- `implemented-unverified` — a repository implementation or runbook exists, but the required observed proof is incomplete.
- `development-verified` — exact Development proof exists; Production remains unproved.
- `production-ready` — both automated and observed Production proof exist at one reviewed release SHA, with rollback and evidence retained.

## Evidence update protocol

1. Record environment, reviewed 40-character Git SHA, actor, timestamp, and result in the named evidence location.
2. Link automated proof to the exact test command and receipt; a test filename alone is implementation evidence.
3. Link manual proof to an observed receipt, including the negative or rollback step.
4. Change only the row whose evidence changed. Never infer Production from Development or from an applied migration number.
5. A reviewer other than the implementer rechecks every `production-ready` transition before Jonathan approves meaningful October use.
