# Architecture

## Runtime

Hearth is a TypeScript household ledger with a React interface. The domain lives in `src/core` and does not import React, DOM, or storage. The UI in `src/App.tsx` is an untrusted client: it may format, filter, and preview, but every write goes through a command that validates plain data and returns a new household snapshot.

The accepted target is Google-account cloud continuity (D-114): a signed-in person discovers their personal ledger and household memberships from any device; no device is the host. The cloud is the durable continuity layer, while every device uses PGlite as its validated accounting engine and offline replica. D-114 implements the disposable-Development bridge in the following transitional stack:

1. **Command replicas** — IndexedDB `hearth-ledger` / store `households`, plus a `localStorage` fallback. Either durable device store may carry an accepted snapshot; large ledgers that exceed the small `localStorage` quota remain valid in IndexedDB, while the tiny catalog and active pointer stay in `localStorage` when possible. Acceptance fails closed only if neither store can save the snapshot. Household snapshots are keyed by environment + household id, and signed-in personal rows are also stored in a member-only envelope keyed by environment + household + member. Legacy environment-only snapshots migrate on read. Commands still operate on the accepted full household snapshot so reconciliation cannot drop a partner's personal facts.
2. **Books** — a double-entry PostgreSQL database in PGlite (`idb://hearth-books-development` or `idb://hearth-books-production`). Each database contains the currently active household's compiled books; changing replicas transactionally replaces those rows because catalog ids are household-local. Inactive durable snapshots remain in the v2 replica store and are re-ingested when selected. After every save the active snapshot is posted as balanced `journal_entries` / `journal_lines`. Views expose trial balance, income statement, net worth, and an unbalanced-entry alarm. D-161 adds constrained operational `household_funds`, monthly-plan, append-only event/allocation, and custodian-private reconciliation tables. The Fund is deliberately absent from `chart_accounts`: it is an ownership/clearing subledger over real posted purchases, not cash Hearth holds and not a second bank balance. **PGlite is the books engine.**
3. **Development continuity bridge** — exact Google membership is discovered through Auth JWT / continuity membership rows (legacy open snapshot scan only when membership tables are missing). Signed-in writes enqueue the latest accepted full snapshot locally, retaining the earliest expected hosted revision and confirmation ids, then retry on launch/focus/reconnect. Legacy `linked`/phrase transport remains. The app does **not** fill the hosted normalized journal tables.

**Startup authority (D-175):** the synchronous local-storage replica may paint the kitchen shell immediately, but it is display-only until a generation-bound PGlite inspection agrees with that exact environment, household, and canonical financial hash. Confirm and all active-household mutation paths stay closed while validation is pending or blocked. Missing/incomplete schema may rebuild then re-inspect; mismatched, interrupted, or invalid stored books never silently rebuild. Browser PGlite runs in a module worker when IndexedDB, Web Locks, Worker, and BroadcastChannel support are present, while tests and unsupported browsers keep the direct engine. Linked network fetch and Realtime attachment start only after local readiness; the fetch never occupies the local write queue, and every returned candidate still crosses queued `acceptHouseholdWrite` before display. Metadata-only revisions may reuse the latest matching financial receipt, but readiness carry-forward compares canonical financial facts before persistence. Secondary rooms are behavior-level lazy chunks; the basic shell and bounded Hercules presence stay eager.

D-114 supplies Development Google discovery, compacting outbox replay, automatic pull/focus/reconnect synchronization, multi-household local replicas, explicit switching, and a dedicated member-personal device replica. Migration 003 is applied, so D-117 hosted membership rows plus member-personal hosted snapshots are live in Development: discovery is server-filtered and the personal scope overlays the matching member before PGlite acceptance. Missing tables deliberately fall back to the D-114 open-snapshot bridge. D-122 monotonic snapshot CAS via `rpc/publish_household_snapshot` is **live on Development** (migration `002_snapshot_cas.sql` applied 2026-08-25) with outbox acknowledgement and exponential backoff; Auth/continuity paths **refuse** GET-compare-POST when the RPC is missing (D-147). **D-149** reframes sync toward Tier 1 Realtime **100–500 ms** partner visibility and Migration **012** atomic Shared+Personal SQL; see [`SYNC_ARCHITECTURE.md`](SYNC_ARCHITECTURE.md). D-123 deny-by-default RLS **006 is applied** with Google Auth live; Create / invite smoke and Production readiness remain open. Every pulled or merged money state passes the same environment, accounting, and idempotency acceptance boundary before persistence or display. Phrases and Hearth Pass files may remain invitation, export, backup, or recovery tools; they are not normal storage authority.

Deny-by-default Auth/RLS cutover **006 is applied**: anon household REST is revoked; access is membership-bound. Through 2026-09-30 Development data remains disposable fixtures, not October household data. Credentials, schema application, Production changes, and destructive cleanup are not covered by the disposable-data policy.

D-137 adds a second, fail-closed cloud command adapter for optional Hercules Pro writes. Member-owned Personal/Household consent lives only in the Personal envelope and is rechecked at confirmation. `prepare_transaction` runs the ordinary deterministic command and books gates but does not persist. D-163 extends the same two-step boundary to eligible worked Evidence: `shift_write_options` returns a short-lived opaque candidate, `prepare_shift_from_evidence` reruns ordinary `postWorkShift` without persistence, and `confirm_shift_from_evidence` rechecks the immutable server-owned bundle, both affected-ledger permissions, membership, base revision, identity, and books before publication. Notification email and schedules never appear as worked candidates. A short-lived encrypted preview binds the Google/Supabase identity, environment, household, member, ledger, base revision, exact generated rows, and command identity. After ChatGPT displays that preview and the person explicitly confirms it, `publish_hercules_confirmed_write` atomically advances shared CAS, records the exactly-once receipt, and updates the Personal envelope when needed. It has no legacy GET/POST fallback. Missing RPC, stale revision, expired preview, opt-out, wrong membership, changed evidence, or invalid books means zero write. Devices later pull and validate the cloud result into PGlite; no device must be online for the ChatGPT write.

D-139 adds a decoupled MCP Apps presentation surface to the same authenticated `/mcp` server. `summon_hercules` returns only mood/headline/short line/ledger label and links a versioned HTML resource. ChatGPT executes that resource on a sandbox origin, so the Worker adds cross-origin headers only to the public companion module, under-3-MB preserved-rig GLB, and Hercules mark; the MCP endpoint and all other site assets remain closed. Independent module/model deadlines replace permanent `Waking Hercules…` with the static mark when 3D cannot start. The resource requests picture-in-picture and otherwise stays inline. Accounting tools remain UI-less so repeated reads do not remount the companion. The iframe receives no ledger credentials or command authority; the ordinary OAuth, grounding, and confirmed-write boundaries remain unchanged.

The website is Cloudflare Workers + Assets (`hearth-books`). Download SQL from the Books tab still loads the PGlite schema elsewhere.

Pairing today: every household has a three-word phrase, join link, and Hearth Pass. These remain useful invitation/recovery mechanisms. D-114 makes Google identity plus durable membership the normal new-device entry; the phrase is routing, not authentication or durable authority.

The in-memory command clones JSON. **It is not accepted books** until `acceptHouseholdWrite` validates cents and double-entry, ingests PGlite inside a transaction, persists the snapshot, and only then may transport a linked household. Failure at any step keeps the previous valid household readable and unpublished. Undo still restores a whole snapshot (not yet a reversal receipt). Concurrent catalog adds still merge by id on pull/push. A linked save reconciles with the hosted snapshot, then performs **one** upsert; local PGlite ingest does not push again.

Catalog rows (`Account`, `Category`, `Goal`, `BudgetPlan`, `Member`, `Activity`, `Preset`) last-write-win on required `updatedAt`. Goal progress is append-only `goalContributions`; `savedCents` is the sum. **Journal facts are not auto-merged.** A transported write states the `baseRevision` it extends; a stale hosted revision becomes a visible conflict bundle (`conflicts[]`) and does not disappear after refresh. Preferred transport is `rpc/publish_household_snapshot` (D-122, live on Development). The client falls back to GET-then-compare-then-POST only when PostgREST reports the RPC missing. Audit hashes cover financial meaning, not timestamps. Demo / empty / Pass / non-member households make zero continuity REST calls; a matching signed-in Development identity may transport without `linked: true` (D-114). Claude consumes `src/claude/commandContract.ts` rather than inferring success from toasts.

D-161 extends the same atomic Shared+Personal continuity envelope and command log without a new public hosted table. `Account.scope` defaults legacy rows to `shared`; `personal` account metadata is split into only its owner's Personal envelope. Fund config, plans, immutable events, settlement allocations, Kitty allocations, and transaction funding are Shared. Bianca's backing-account binding, full bank total, Personal remainder, and unexplained difference are Personal only. Shared reconciliation exposes only the Fund slice and tied/not-tied result. Fund event/allocation same-id divergence becomes a conflict instead of last-write-wins. Audit and command identity hashes include Fund financial meaning.

D-162 does not broaden command authority. The existing encrypted Flinks Worker/D1 boundary may later provide Bianca-private, sanitized bank evidence after a separate Release review. Raw provider rows, tokens, account identity, and balances never enter continuity snapshots, PGlite Shared facts, Hercules context, or model prompts. Matching can verify an already confirmed D-161 event; it cannot create a contribution, purchase, settlement, or balance change.

## Layers

1. **Catalog** — members, accounts (chequing / savings / credit / investment / other / receivable), categories, effective-dated work jobs/roles, appointments, claims, presets.
2. **Commands** — `postEntry`, `postTransfer`, batch intake `buildBatchImport` (D-130; staged rows only, then ordinary entry/transfer commands under one undo), legacy `postShift`, job-based `upsertWorkJob` / `clockInShift` / break and clock edits / `postWorkShift` / `settleWorkReceivable` / `payDeferredWorkTipOut`, `addCategory`, budget, goals, recurrences (`addRecurrence`, `adoptRhythm`, `postOneRecurrence`, `postDueRecurrences`), appointments / claims `addAppointment` / `postVisit` / `openClaim` / `settleClaim` / `writeOffClaim` / `submitClaim` / `acceptVisitGoal` (D-053; settle is a transfer, never income; Hercules proposes jars and does not `addGoal` unprompted), presets `addPreset` / `acceptPresetNotice` / `archivePreset` / `dismissNotice` (D-058; never post money), account floor `addAccount` / `updateAccount` / `archiveAccount` / `markInvestmentValue` / `postCardInterest` / `postCardRewards` / `postSavingsInterest` (D-047; marks never post; interest/rewards still `postEntry`), D-161 Household Fund setup/plan/contribution/settlement/reconciliation/Kitty/reversal/direct-debit commands, cosmetic `scribbleChalk` / `equipCosmetic` (D-042, D-044), Hercules desk `recordHerculesTalk` / `forgetHerculesMemory` / `wipeHerculesChat` (D-049; never post money), Audit Office `recordReconciliation` / `closeBooksMonth` / `reopenBooksMonth` (D-046 / D-084; close is a hard lock; reopen is explicit; never post money), sit-down `applySitDown` / `saveSitDownSession` / `executeSitDownMoves` / `reversePostedMoney` (D-083–D-085; leftover plan then transfers; reverse instead of delete), and Google-bridge `linkGoogleIdentity` / `setGoogleServices` (D-043) plus Drive create-only month workbook (D-087). Each clones state, writes, refreshes duplicate flags, appends activity, and returns an undo snapshot. Cosmetics, clock/break edits, rec, close, marks, Hercules talk, presets, reports, Google, and the unconfirmed import inbox never post money. Sit-down Confirm moves leftover through `postTransfer`.
3. **Books** — `compileHousehold` turns each money document into balanced debit/credit lines. PGlite stores them. Health Check refuses a household whose trial balance or accounting equation is off.
4. **Projections** — `monthSummary`, `weekSummary`, `buildDashboard`, `runHealthCheck`, `sitDownPreview`, `leftoverProjection`, `sitDownFacts`, `trialBalance`, `detectRhythms`, `detectHabits`, `composeNotices`, `buildMonthBoard`, `askBooks` / `askHercules`, `describeCompanion`, `herculesBriefing`, `composeHerculesChatRequest`, `householdWallet` / `creditCardView`, `auditOpinion`, `balanceSheet`, `incomeStatement`, `cashFlowStatement`, `statementOfChangesInEquity`, `liquidityWatch`, `notesToFinancialStatements`.
5. **Google engine** — Google identity is Development account entry, ledger discovery, and recovery (D-114). Calendar, Drive, Contacts, Gmail, and Sheets remain separate opt-in integrations; they never `postEntry`, and Drive/Sheets are not the ledger. D-163's direct Gmail import is an explicit, cancellable PWA action using short-lived `gmail.readonly`; a fixed 7shifts query plus exact RFC822 sender verification uploads matching raw messages to the encrypted member Evidence vault. Gmail tokens never reach Evidence or Hercules and no refresh token is stored server-side. Tokens and hosted sessions never enter ledger snapshots, the outbox, or Git.
6. **Kitchen Worker** — Cloudflare Workers + Assets (`hearth-books`). HTML is `Cache-Control: no-store`. `POST /hercules/chat` accepts only the live kitchen, the exact Git `main-` production alias, localhost, and eight-hex Worker previews; arbitrary named aliases remain denied. It meters 60 requests per client IP per UTC day in KV when bound and isolate memory otherwise, with missing IP metadata sharing an `unknown` bucket rather than bypassing the counter (D-103 / D-121). The memory fallback is not globally consistent; bind KV for reliable production enforcement. Chat uses OpenAI or Anthropic when those **Worker secrets** are set, then Cloudflare Workers AI (D-045, D-059). Third-party keys are allowed; they must never be `VITE_` or household rows. Free in-app Hercules cannot post money, invent notice keys, or treat ledger text as instruction. Briefing, notices, ledger, memories, grounded copy, and allowed figures are rebuilt from the signed-in member's disclosure projection at the outbound boundary (D-115). The phone applies or records a delayed answer only while request id, environment, household, and member still match (D-116). Local Vite falls back to `localHerculesChat`. D-130 adds `POST /documents/scan` at the same origin door and meter. It accepts one selected JPEG/PNG/WebP data URL, tries OpenAI vision then Anthropic image input, sanitizes a strict financial-document shape, and never writes images or money. Jonathan approved its Development Worker deployment; Actions run `32872129163` published it on 2026-08-25 and live origin/CORS/fail-closed smoke passed. The separate `/mcp` surface is Google/member scoped: reads are deterministic; D-137's optional write contracts advertise their separate security requirement but are executable only with `hearth.write` and still require the two-step sealed confirmation boundary.
7. **UI** — Home is the September Office (D-051 / D-079 / D-080 / D-082 / **D-156**): **mobile** (`< 720px`) is `OfficePhone` (glance + one-tap, three stamps, five or fewer objects); **wide** default is the composed paper office (`OfficeWide`: seals, mosaic, hero blotter, side notebook, paper infographics) with rainy window and Hercules wander. ## Dual Course coupling

Family-office accounting (weight **5**) and Hercules / interactables (weight **3**) share this kernel. There is no second ledger for the cat.

- Course A writes through commands, then `compileHousehold` into PGlite. Health, statements, wallet, rec, and close are projections.
- Course B **reads** those projections (`describeCompanion`, `herculesBriefing`, `auditOpinion`, `householdWallet`, `talkHercules`, `planHerculesTurn`, `composeNotices`). Cosmetics and Hercules desk writes (`scribbleChalk`, `equipCosmetic`, `recordHerculesTalk`, `addPreset`, `acceptPresetNotice`) clone the snapshot and never put money ids in `postedIds` except the preset catalog id. Journal questions skip the model.
- A new accounting surface must expose at least one companion line, unlock, chalkboard, wallet tile, or ceremony.
- A new companion behavior must be grounded in a posted fact or a Health / rec / close / wallet projection.
- If they conflict, Course A wins. Product law: [STRATEGY.md](STRATEGY.md), D-048.

## Data-model rules

- One canonical `transactions` array is the command document. The books compile each document into balanced `journal_entries` / `journal_lines`. A Visa payment is one journal entry: debit the card, credit chequing. A TFSA contribution is debit investment, credit chequing (cash-flow investing out).
- Amounts are integer cents. Currency is CAD copied from the account.
- Dates are `YYYY-MM-DD` civil keys in `America/Toronto`. Week bounds are computed from that civil date, never from `Date#setHours(0,0,0,0)` in the runtime zone.
- `expense` and `income` affect totals. `transfer` is a paired movement between accounts and is excluded from both. `refund` subtracts from category spend.
- Ownership is a `splits` array that must sum to the amount. Joint is explicit. A split can be any percentage; the leftover cents go to the last person so the total is exact.
- Every transaction and shift has `createdBy` and `visibility` (`household` | `personal` | `both`). Home, Plan, and Ledger filter that view. Health Check still runs on the full snapshot.
- `duplicateKey` is an exact fingerprint. Posting also scores similar rows: same type, same amount, within five Toronto calendar days, plus shared notes, place, category, or source. Partner personal rows are not part of that scan. `potentialDuplicate` is derived from that. `isDuplicate` remains the reviewed financial control.
- `src/core/importInbox` parses and normalizes selected external documents without mutation. Exact FITID/document provenance wins at 100 confidence even before account mapping; otherwise it reuses the ordinary similarity scorer. `>90` starts cancelled, `50–90` is unresolved, and `<50` starts kept. Ambiguous accounts remain blank. D-137 separately proves available statement equations and receipt numeric components, then finds unique exact-cent receipt/payment subsets within the active member/view projection. Payment claims are one-receipt-only; large candidate sets require human choice instead of silently becoming “unmatched.” The staged UI and delayed callbacks are bound to environment + household + member + view. Evidence matching never posts. The review may exclude an old row through `markDuplicate`; it never deletes history. Final `buildBatchImport` remains the only import money-write surface.
- Recurring definitions stay separate from posted rows. Appointments are a separate catalog (D-053) projected onto the same month board as `visit` items, and Calendar → Appointments is the destination for history, itemized bills, claims aging, and the METC log (D-056). Presets are a separate catalog (D-058) for one-tap Add; they never post by themselves. Posting a visit uses `postVisit`; posting a bill still uses `postEntry` after confirm. Google and ICS never write the books.
- Claims (`Claim`) are shared household facts with `updatedAt`. Merge is last-write-wins like recurrences. Audit `snapshot_hash` includes expected / received / written-off cents.
- Goals are data. Shared goals appear on Home. Personal goals are a filter only — not a privacy boundary. Progress is append-only contribution rows; `savedCents` is derived. Ask and Plan can name who put money in.
- Kitchen cosmetics (`kitchen.chalkboard` including optional `ink`, Hercules companion + `kitchen.hercules` chat/memories, `kitchen.openShift`, `kitchen.games`) are shared household data. They merge and tombstone like recurrences. They are not journal lines. `kitchen.books` (recs and closed months) is the Audit Office desk: also shared, also never journal lines. Reopen tombstones `CLOSE-YYYY-MM`.
- Google links (`google.links`) are shared household data: who is signed in, not the token. Tokens live in `localStorage` per environment and member. Both Supabase **Continue with Google** and the direct Google suite request narrow `drive.file` at account connection under D-137; receipt retention remains per-image and other Google services remain household-wide opt-ins. Raw receipt bytes and Drive ids never enter the snapshot.

## Shift boundary

Legacy `calcShiftAmounts` remains for legacy D-028 rows. D-127 job shifts use `calculateWorkShift` for both preview and `postWorkShift`; the job/rate fingerprint makes an effective-dated rule change fail closed instead of silently changing the review. `kitchen.openShifts` stores member-keyed, mergeable device timelines plus paid/unpaid breaks and never posts money. Confirm recognizes take-home wages in the job's Wages owed receivable, paid breaks as their own income category, card tips in Card tips owed, same-day cash tips in Cash, and configured tip-out expenses. `settleWorkReceivable` later transfers the receivable without recognizing income again. Reversed/replaced shifts remain visible but are excluded from overtime, Calendar, obligations, and reports. D-155 remains the default manual Timesheet inbox. **D-158** adds a separate member Evidence Worker: authenticated capture → per-object encrypted private R2 + D1 metadata → deterministic sanitized derivation/bundle → Shift Evidence Center. **D-160** duplicates that plane across physically separate Development and Production D1/R2/Queue/key bindings; environment is part of every authenticated owner tuple and encryption context. Raw bytes, source URLs, filenames, mail headers, provider ids, hashes, and notes never enter household snapshots or Hercules. D-159's automatic posting path is superseded and hard-disabled by **D-172**. D-172 reconciles mapped schedule/timesheet/Gmail facts into member-Personal `ShiftEnvelope` mail; the ordinary visible Shift Confirm is the sole worked-money door and seals a versioned `ShiftBible`. Tip Science reads the current worked Bible for new envelope-backed shifts. Historical job-place weather is nonfinancial and fail-soft. A sealed Bible schedules contributing raw evidence for crypto-erasure after seven days; the Bible, journal, command receipt, and content-free deletion audit remain. Companion registration is capture-only and revocable; it cannot list evidence, read household data, or invoke commands. See [`SEVEN_SHIFTS_EVIDENCE.md`](SEVEN_SHIFTS_EVIDENCE.md).

## Trust and failure

Browser controls are usability. Commands throw `ValidationError` before mutating. Duplicate/settings/double-shift cases throw `NeedsConfirmationError` with zero writes. Undo restores the previous snapshot and tombstones posted ids so a deleted row cannot return from the other phone. A write queue prevents overlapping saves and undos. Health Check is a projection, not a hidden sheet.

## Environments

Development is the default local ledger. Production is a second named snapshot on the same device. They cannot be confused by workbook title; the pill in the top bar is the environment and asks before switching.

Current Supabase code supports legacy **linked** transport plus automatic Development transport for an exact signed-in Google member. Additive Auth preparation 004, CAS hardening 005, deny-by-default cutover **006**, and SELECT bridge 008 are applied; anon household REST is revoked. Automatic continuity requires Google membership identity (D-143/D-146). ## Scale

Commands currently clone the snapshot per write, which is honest and simple at household scale. The SQL journal is the queryable, constraint-backed record of those writes. **D-148** schedules Tier 2 command-log primary and Tier 4 normalized hosted journal as the scale path; do not populate `001` normalized tables as transport until Tier 4 design passes review ([`SYNC_ARCHITECTURE.md`](SYNC_ARCHITECTURE.md)).
