## Goal

Make CAD the authoritative currency for current household accounts and transaction records. Jonathan confirmed that the existing values labeled `USD` are CAD amounts with an incorrect label. This release changes labels and configuration only: it must not perform exchange-rate lookup, multiplication, rounding, or any other amount conversion.

## Runtime design

`Accounts.Currency` is the source of truth. `getActiveAccount_()` requires exactly one active account with a nonblank stable ID and the supported currency `CAD`. Add Transaction and Add Shift resolve that account before their write path and copy its currency into both record layers:

- `Raw Transactions.Raw_Currency`
- `Transactions.Currency`

The writers refuse a missing account, multiple active accounts, or any unsupported currency. This preserves the current no-selector interface while enforcing D-022: an explicit account selector is required before multiple active accounts can be enabled.

The Data Health Check now detects unsupported account currency, unknown or ambiguous record account links, and any Raw Transactions or Transactions currency that disagrees with its account. Diagnostics also requires all three currency headers.

## Guarded development migration

Two development-only menu actions appear only when the source is exactly v0.0.30 and the spreadsheet title exactly matches `devCopy of Budget_App__v 0.23`:

1. **Preview v0.0.30 CAD Corrections** is read-only. It scans the real live extent of Accounts, Raw Transactions, and Transactions, identifies each row by its stable ID and account link, accepts only the known transition `USD` to `CAD` or an already-correct `CAD` value, and lists every pending cell.
2. **Apply v0.0.30 CAD Corrections…** requires the exact phrase `APPLY V0.0.30 CAD TO DEV`. It rebuilds the plan under a document lock, rejects any plan drift, journals each attempted write, verifies every final currency, and compares protected row fingerprints that exclude only the currency column.

If any write or verification fails, Apply reverses its attempted currency changes and re-reads every target to prove recovery. If recovery cannot be proven, it fails loudly and instructs the user not to retry until the development Sheet is inspected. A second successful run is a verified no-op.

The migration is dynamic rather than tied to the retained snapshot's row count. Based on the last live v0.0.29 evidence, the expected development preview is likely one Accounts cell plus 39 Raw Transactions cells plus 39 Transactions cells, but the preview output—not this estimate—is authoritative.

## Protected data

The migration cannot intentionally change:

- amounts or financial totals
- dates or time-zone values
- categories or subcategories
- ownership/member links
- tips, wages, sales, or tip-out values
- transaction IDs, raw IDs, or batch links
- helper formulas, duplicate keys, or duplicate decisions
- budget, dashboard, or income-history calculations

It does not run the budget summary refresh because currency metadata is not an input to current financial calculations.
