# Operation vocabulary — foundation spike

Source: `origin/main@44c5931`, inspected 2026-09-07. This is a producer-complete audit and a blocked wire freeze, **not a claim that existing commands already implement A/B/C/D**. No money semantics are changed here.

## Blocking discoveries — read before implementing Prompts 3 or 4

1. **The existing vocabulary is not finite.** `CommandReceipt.commandKind` is `string` (`src/core/types.ts:1164`). `src/App.tsx:3727` assigns `token?.commandKind ?? token?.label ?? "commit"`; `commands.ts:1509` supplies the human summary as `undo.label`. Most commands therefore emit arbitrary names, dates, amounts and notes as their receipt kind. The table covers each producer family; it cannot enumerate infinitely many resulting strings. The new protocol needs a closed, stable discriminated union, not a grep-derived string allowlist.
2. **Money deletion is a current, live behavior.** `src/core/confirmationUndo.ts:66` deletes transactions, shifts, contributions, purchases and claims and later writes tombstones. `src/App.tsx:4174` calls that helper; only supported funded transactions take its reversal exception. `commands.ts:5117` also exports a snapshot-restoring Undo. This contradicts the assertion that all money correction already uses reversal ADD. Do not port either deletion path or silently change its meaning: the money-meaning gate requires an explicit resolution.
3. **`markDuplicate` is a money-affecting SET to an A collection.** `commands.ts:4486` changes `transactions.isDuplicate`; the journal excludes duplicate rows. It needs a specified immutable exclusion/reinstatement fact or reversal policy. Calling it catalog SET or DERIVED loses user intent.
4. **The four collection lists omit real product state.** Onboarding lifecycle/progress, rehearsal, workJobs, shiftBibles, coworkerAttendance/Schedules, fundPrivate, devices, google, calendar and kitchen state are neither listed catalog nor derived data. Creating or updating appointments/coworkers is not a TOMBSTONE. Explicit NO-FIT is preferable to inventing a fifth accepted wire class.
5. **Many commands are atomic multi-class bundles.** Contribution/purchase commands append facts and update goals; recurrence posting appends money and advances the recurrence; Shift Confirm appends money and resolves a private envelope. A single old command cannot honestly receive exactly one primitive class. The DO can serialize one UUID envelope containing typed A/B/C primitives atomically, but that envelope contract must be agreed before the wire freeze.
6. **Listed grow-only collections are mutable today.** Onboarding submission replacement sets the previous row's `supersededBy` (`commands.ts:843`); sit-down rows are upserted and their Drive id later edited; claims change state and settlement amounts. Their immutable event forms are not specified by the task.

## Classification contract

A = immutable ADD, union by client UUID; the DO deduplicates and rejects conflicting reuse. B = catalog fields SET by `(lamport, actorId)` with owner/authority checks before merge. C = remove-wins tombstone on authorized nonfinancial rows. D = recomputed projection, never transported. **NO-FIT is an explicit assigned finding, not an unreviewed row or an accepted fifth operation.** A/B/C below describe the proposed primary data primitive, after universal activity/receipt/projection handling; a compound or omitted-collection command stays NO-FIT.

All `commit()` producers also append `activity`, update local timestamps/transport bookkeeping, recompute `transactions.potentialDuplicate`, and cap activity to 200 (`commands.ts:1482`). Activity is an A fact with a separate retention policy; pruning the local window must not become a financial tombstone. Potential-duplicate flags, `booksAcceptedHash`, revision/baseRevision, balances, trial balance, books equation, month summaries, dashboards, run rate, fund levels and streaks are D. Command receipts are delivery/audit metadata keyed by the operation UUID, not permission to re-post. Existing locally allocated sequential row ids are not client UUIDs and need protocol identity mapping.

Scope means the maximum producer reach, **not permission to broadcast the entire command**. `both` must be partitioned into a shared projection and member-owned personal payload; account scope, transaction visibility/createdBy, goal ownership and member ids remain enforced server-side. A shared activity summary must not disclose Personal labels or values. Private workplace state is owner-only.
